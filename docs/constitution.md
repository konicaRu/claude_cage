# Конституция проекта Claude Cage

## 1. Проверяемость важнее предположений
Не объявлять этап готовым без реального прогона соответствующего Gate. Документировать только подтверждённое состояние; планы и гипотезы помечать явно.

## 2. Одно изменение — одна проверка
Не менять одновременно несколько системных, сетевых или виртуализационных параметров. При проблеме: воспроизведение → доказательства → гипотеза → минимальное изменение → повторная проверка.

## 3. Секреты никогда не попадают в Git
Proxy credentials, токены, cookies, session data, API keys, приватные ключи и другие секреты хранятся только локально подходящим безопасным способом. Перед commit/push выполнять sanity-check.

## 4. Минимальное вмешательство в Windows
Не изменять Windows, Hyper-V/VMP/WSL, firewall, DNS, маршрутизацию или security-настройки без подтверждённой необходимости. Перед потенциально опасным изменением объяснить последствия и запросить подтверждение пользователя.

## 5. Стабильный сетевой контур
Цель — один настроенный dedicated static ISP egress для среды Cage без необходимости системного VPN Windows. При сбое proxy нельзя молча считать прямой fallback приемлемым: поведение должно быть проверено и задокументировано.

## 6. Никакого обхода защит
Проект не реализует ротацию аккаунтов/IP, подмену идентичности или механизмы обхода ограничений сервиса. При отказе сервиса зафиксировать ошибку и диагностировать поддерживаемую конфигурацию.

## 7. Upstream проверяется перед применением
Перед установкой внешнего plugin/skill/tool проверять актуальные официальные README, releases и инструкции. Старые команды из project-starter или документации проекта не считать автоматически актуальными.

## 8. Минимализм зависимостей
Не устанавливать plugin/skill/tool «на всякий случай». Подключение должно решать конкретную текущую задачу и не дублировать уже выбранный процесс без пользы.

## 9. Git — точки безопасного отката
После законченного проверяемого этапа обновить MEMORY.md и ARCHITECTURE.md, проверить отсутствие секретов, затем commit/push. Разрушительные Git-команды — только по явному решению пользователя.

## 10. Источник правды
При расхождении документации с реально проверенным состоянием системы источником правды является фактическая конфигурация/результат теста; документацию после этого актуализировать.
